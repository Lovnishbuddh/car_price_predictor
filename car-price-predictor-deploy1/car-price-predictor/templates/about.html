Project Details

Everything about how this Car Price Predictor was built — dataset, workflow, algorithms and results.

1. The Problem

India's used-car market is huge and unorganized. Two identical-looking cars can be quoted very different prices, and buyers/sellers have no reliable way to know a fair price. Goal: build a Machine Learning model that predicts a realistic resale price from the car's basic specifications.

2. The Dataset

quikr_car.csv — used-car listings scraped from Quikr.com.

Data quality issues found and fixed (this dataset is deliberately messy, which makes cleaning the most interesting part):

  • 35 listings with "Ask For Price" instead of a number → removed
  • Years stored as junk text ("r 15", "TOUR", "150k") → removed
  • Prices as comma-strings ("4,25,000") and one impossible 85,00,003 → parsed & range-filtered
  • Kilometres as text ("45,000 kms"), blanks, and a 4,00,000 km outlier → parsed & capped
  • 55 rows missing fuel type → removed
  • Brand names in mixed case (MARUTI, tata) and fake sellers ("URJENT") → normalised & filtered

Result: 892 raw rows → 797 clean rows, 18 brands, 242 models, prices from Rs 30,000 to Rs 29 lakh.

3. The Machine Learning Workflow

  1. Load the raw CSV with pandas
  2. Clean it (rules above) in src/preprocess.py
  3. Engineer a feature: year → Car_Age = 2026 − year (age drives depreciation)
  4. Encode categories: OneHotEncoder turns name / company / fuel_type into 0–1 columns
  5. Split: 80% training (637 rows) / 20% testing (160 rows)
  6. Train three algorithms and compare them fairly
  7. Evaluate with R², MAE, MSE, RMSE + 5-fold cross-validation
  8. Save the best model with joblib → models/car_price_model.joblib
  9. Serve: Flask loads the model once and answers /predict requests

Why tree ensembles? A car's price does not depend on its features in a straight line — a 5-year-old luxury SUV behaves very differently from a 5-year-old hatchback. Decision-tree ensembles capture these non-linear patterns and interactions automatically, are robust to outliers, and work well without feature scaling. Extra Trees ("Extremely Randomized Trees") is Random Forest's cousin: it also builds many trees and averages them, but picks split thresholds randomly, which adds diversity and reduced overfitting — and it won our comparison.

5. Evaluation Metrics Explained

  • R² (coefficient of determination) — how much of the price variation the model explains, from 0 to 1. Our CV value {{ meta.metrics[meta.best_model].cv_r2_mean }} means roughly {{ (meta.metrics[meta.best_model].cv_r2_mean * 100) | round(0, 'common') | int }}% explained.
  • MAE (Mean Absolute Error) — average miss in rupees; on average predictions are off by about Rs {{ '{:,.0f}'.format(meta.metrics[meta.best_model].mae) }}.
  • MSE / RMSE — squared error punishes big misses; RMSE (Rs {{ '{:,.0f}'.format(meta.metrics[meta.best_model].rmse) }}) is in rupees again.
  • Cross-validation — the 797 rows are split into 5 folds; the model is trained and tested 5 times so every row is tested once. More reliable than a single train/test split.

7. Advantages, Limitations & Future Scope

Advantages

  • Instant, data-driven price estimate instead of guesswork
  • Handles messy real-world scraped data through a documented cleaning pipeline
  • Simple, fast, runs on any laptop; model is versioned with joblib

Limitations

  • ~800 rows is small; rare brands/models are learned poorly
  • Features are limited — no transmission, owner count, location or accident history
  • Data is from one website and a few years old

Future Scope

  • Add features (transmission, owners, city, accident history) from a larger scrape
  • Retrain regularly so prices track the live market
  • Deploy on the cloud with a proper frontend and user accounts
